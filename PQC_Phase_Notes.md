# AgePony 3.0.0 — PQC Phase A (Android core): MLKEM768-X25519 hybrid recipient

Adds the standardized post-quantum age recipient (`mlkem768x25519`, `age1pq1…`) to
`agepony-core`, interoperable with the `age` CLI v1.3.0+. This is the crypto core only;
UI (identity generation, recipient book, migration) comes in later phases.

## What's in this drop

New files under `agepony-core/src/main/kotlin/com/agepony/core/`:

- `crypto/Sha3.kt` — SHA3-256 + SHAKE256 (Bouncy Castle) for the hybrid KEM.
- `crypto/MLKEM768.kt` — thin BC wrapper: deterministic ML-KEM-768 keygen from a
  64-byte seed, deterministic/random encapsulation, decapsulation.
- `crypto/HpkeMlkem768X25519.kt` — the MLKEM768-X25519 hybrid KEM (a.k.a. X-Wing) +
  single-shot HPKE (RFC 9180) base mode. Self-contained, mirrors what the iOS hand-roll
  will do.
- `recipients/Hybrid.kt` — `HybridRecipient` / `HybridIdentity` (`age1pq` /
  `AGE-SECRET-KEY-PQ-`), producing/consuming the `mlkem768x25519` stanza. Mirrors
  `recipients/X25519.kt`.

Modified:

- `bech32/Bech32.kt` — raised the decode length cap (was 1023) so ~1960-char `age1pq1…`
  recipients decode. age applies no bech32 length limit; we keep a generous sanity cap.

Test:

- `recipients/HybridRecipientTests.kt` — known-answer tests pinned to the reference.

## The construction (exact)

- Identity = 32-byte seed (`AGE-SECRET-KEY-PQ-` payload). `SHAKE256(seed)` yields the
  64-byte ML-KEM key seed (`d‖z`) then the 32-byte X25519 scalar.
- Public key = `ek_PQ(1184) ‖ ek_T(32)` = 1216 bytes (`age1pq` payload).
- KEM shared secret = `SHA3-256(ss_PQ ‖ ss_T ‖ ct_T ‖ ek_T ‖ 0x5c2e2f2f5e5c)`;
  `enc = ct_PQ(1088) ‖ ct_T(32)` = 1120 bytes.
- HPKE suite: KEM `0x647a`, KDF HKDF-SHA256 (`0x0001`), AEAD ChaCha20Poly1305 (`0x0003`),
  `info = "age-encryption.org/mlkem768x25519"`, empty aad.
- Stanza: type `mlkem768x25519`, args = `[base64(enc)]`, body = 32-byte HPKE seal of the
  16-byte file key.

## Provenance of the test vectors (why we trust interop)

Vectors were generated by building the actual `filippo.io/hpke` reference (the code age
v1.3.0 uses) and emitting a deterministic seed→ek, enc, and body. Separately, the HPKE
key-schedule + AEAD layer was reproduced from scratch in plain JDK crypto and confirmed to
match the reference's intermediate `key`, `base_nonce`, and `body` byte-for-byte. So the
whole path is pinned to reference output; `HybridRecipientTests` fails loudly if anything
drifts.

## ⚠️ The one thing to verify on your build: Bouncy Castle ML-KEM must be FIPS 203 *final*

This is the only piece that couldn't be exercised in the authoring sandbox (no BC there).
The lattice math is delegated to `bcprov-jdk18on`. FIPS 203 *final* changed key derivation
vs the earlier ML-KEM draft (IPD) — the two derive **different keys from the same seed**, so
a draft-era BC would fail interop.

- `bcprov-jdk18on:1.78.1` (current pin) shipped an X-Wing implementation, so its ML-KEM may
  already be final — but BC 1.79 is explicitly "Latest NIST PQC Standards," leaving this
  ambiguous.
- **The gate:** run `:agepony-core:testDebugUnitTest`. If
  `publicKeyDerivedFromSeedMatchesReference` (and the wrap/unwrap KATs) pass, your BC is
  FIPS 203 final — done. If they fail, bump `bcprov-jdk18on` to **1.81** (definitively final)
  in `agepony-core/build.gradle.kts` and re-run. The classic BC APIs the rest of the module
  uses (SHA-256, HKDF, ChaCha20Poly1305, X25519) are stable across 1.78→1.81, so the existing
  200 tests should stay green — please confirm by running the full suite.

## Follow-ups (later phases, tracked in the 3.0.0 plan)

- Enforce "PQC recipient can't be mixed with non-PQ recipients" at the encrypt-flow layer
  (the reference does this via a `postquantum` label; core currently treats the stanza like
  any other).
- Identity generation + storage, recipient address book (with quantum-safe badge), the
  re-encrypt migration tool, and the iOS hand-roll (same construction, ML-KEM by hand).
