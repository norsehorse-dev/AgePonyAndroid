# AgePony Android 4.0.0 — plan

Working document for the 4.0.0 release. `versionCode 10`, `versionName 4.0.0`.
Companion to `PLANNED_FEATURES.md` (items referenced below) and, on the release
side, `AgePony_3.2.0_Release.md`, whose clean-clone build procedure carries over
unchanged. Last updated: 2026-08-09.

Two features, one headline: the full signing surface (parity with the iOS Sign
tab, plus RSA signing, which iOS-parity alone would not give us), and the
duress/decoy wipe. Both trace back to Simun Petrus's suggestions from Aug 2026;
signing is also the older standing gap that 2.0 built the machinery for and no
release since has surfaced.

---

## 1. Where signing on Android actually stands

The folklore version ("iOS has SSH signing, Android never got it") is wrong in a
useful way. The survey found the crypto and the services all present and tested;
what never landed is the UI, and one vault model. That changes the shape of the
release: this is mostly Compose work against code that already works, not a
crypto port.

### Already on Android, do not rebuild

| Piece | Where | State |
| --- | --- | --- |
| SSHSIG envelope, encode/decode, hashing | `core/signing/SSHSig.kt` | done, tested |
| Software signing: ed25519, rsa-sha2-512, ecdsa-p256 | `core/signing/SSHSigner.kt` | done, tested. RSA and ECDSA exist in core even though no app path reaches them |
| Verification: ed25519, rsa, ecdsa, sk-ed25519, sk-ecdsa, incl. streaming `verifyHashed` | `core/signing/SSHSigVerifier.kt` | done, tested |
| Signed bundle (sign-then-encrypt container) | `core/archive/SignedBundle.kt` | done, used in production flows |
| Sign-then-encrypt | `ui/files/EncryptFlow.kt` | works, but the signer picker only offers software ed25519 identities (`SignerKey`, `EncryptFlow.kt:85`, takes a raw seed) |
| Verify-on-decrypt with trust verdicts | `ui/files/DecryptFlow.kt:366-390` | works |
| Signing service routing software / Keystore hardware / NFC security keys | `app/signing/FileSigner.kt` | complete, **never constructed from any UI** |
| Verification service with trust levels | `app/signing/FileVerifier.kt` | used only inside DecryptFlow |
| Hardware key signing behind biometric prompt | `security/keystore/HardwareKeyService.kt` | done |
| Security key SSHSIG over NFC, with PIN dialog | `security/SecurityKeyService.kt`, `ui/security/SecurityKeyPinDialog.kt` | done |

### Missing, and what iOS has for it

| Gap | iOS counterpart |
| --- | --- |
| Any signing/verifying UI outside the encrypt/decrypt flows | `Features/Sign/`: `SignFileView`, `VerifyFileView`, `SignersView`, `AddSignerView`, `VerifiedBadge` |
| Detached sign (produce `<name>.sig` next to a file) | `SignFileView` + `Services/FileSigner.swift` |
| Detached verify (pick file + `.sig`, get a verdict) | `VerifyFileView` |
| Trusted-signer list. Android's `FileVerifier` matches only the user's *own* identities, so a friend's key can never show as trusted with a name | `Vault/StoredSigner.swift`; matching in `FileVerifier` |
| `allowed_signers` import/export | `Sources/AgePonyCore/Signing/AllowedSigners.swift` + `AllowedSignersTests.swift` |
| "Add this unknown signer" from a verify result | `StoredSigner.Source.fromVerification`, `VerifiedBadge` |
| RSA signing reachable from the app (`FileSigner.kt` throws "RSA signing isn't supported yet") | iOS does not route RSA either; 4.0.0 goes past iOS here |
| Hardware keys usable for sign-then-encrypt | iOS allows Secure Enclave, excludes NFC-style keys (`SignEncryptService.requiresSecurityKey`) |

One honesty note: the README already advertises "Sign and verify with SSHSIG,
using software Ed25519 keys, Android Keystore hardware keys, or a FIDO2 security
key over NFC." Today that is only true inside sign-then-encrypt, and only for
software keys. After 4.0.0 the sentence becomes true as written.

## 2. Feature A — the Sign surface

### A1. Core: port `AllowedSigners`

Port `AllowedSigners.swift` to `core/ssh/AllowedSigners.kt` (it is an OpenSSH
file format, so `ssh/` fits better than `signing/`; move if it feels wrong in
review).

- Parse and serialize the OpenSSH `allowed_signers` line format: principal,
  optional options (`cert-authority`, `namespaces=...`, `valid-after`,
  `valid-before`), key type, base64 blob, optional comment.
- Round-trip guarantee: parse then serialize reproduces semantically identical
  lines, so a file imported from a machine and exported back does not churn.
- Port `AllowedSignersTests.swift` cases as the spec. Add fixture lines
  generated by real `ssh-keygen` to `generate-fixtures.sh`.

Acceptance: an `allowed_signers` file written by AgePony verifies with
`ssh-keygen -Y verify -f` on a desktop, and one written by hand on a desktop
imports without loss.

### A2. Vault: `StoredSigner`

Mirror `Vault/StoredSigner.swift` in the vault, following the existing
`VaultModels.kt` / `Hydration.kt` patterns:

- Fields: id, name (principal), keyType, publicKeyWire (b64), comment, source
  (`PASTE_KEY`, `IMPORT_ALLOWED_SIGNERS`, `FROM_RECIPIENT`, `FROM_VERIFICATION`),
  createdAt. Matching stays a direct wire-blob equality check, same as iOS.
- Vault CRUD + hydration + inclusion in the encrypted blob. Bump whatever the
  vault serialization needs bumped; old vaults hydrate with an empty signer list.
- `FileVerifier` grows a signers parameter. Match order: own identities first
  (a signature made with your own key should carry your identity's name, not a
  signer-list principal), then the signers list; first hit wins and supplies
  the display name. Verdicts stay `TRUSTED` / `VALID_UNKNOWN` / `INVALID`.
- SHA256 fingerprint display helper, same rendering as iOS
  (`FileVerifier.sshFingerprint`), so both apps print identical strings for the
  same key.

Acceptance: a signature from a key on the signers list shows the signer's name
in both the decrypt verdict and the detached verify verdict; deleting the signer
demotes the same file to a valid-but-unknown verdict.

### A3. The Sign tab

New top-level destination in `AgeTab.kt` mirroring iOS's tab structure. This
makes six bottom-nav items against Material's recommended five; see open
question 1 before wiring it, since the answer decides whether Verify lives here
or under Files.

Screens, all mirroring their iOS namesakes in structure:

- **Sign a file**: pick a signing identity (software ed25519, RSA after A5,
  hardware key, security key), pick a file, produce `<name>.sig` via SAF
  `CreateDocument`. Show the `ssh-keygen -Y verify -n agepony` hint line the way
  iOS does, so the desktop side is discoverable.
- **Verify a file**: pick the file and the `.sig`, run `FileVerifier`, render
  the verdict badge. On `VALID_UNKNOWN`, offer "add this signer" with the name
  field prefilled from the sig comment when present (`FROM_VERIFICATION`).
- **Signers**: list (name, keyType, fingerprint), delete, and add via:
  paste a public key, import an `allowed_signers` file, promote a saved SSH
  recipient (`FROM_RECIPIENT`), or the verify-screen path above. Export the
  whole list as `allowed_signers`.

Large files: `FileSigner.sign` currently takes the whole message as bytes. Add
a hashed variant (the core already has `signEd25519Hashed` and
`SSHSigVerifier.verifyHashed`) and stream the digest, so signing a 1 GB file
costs one read and a 64 KiB buffer, matching what iOS's two-pass flow does.

### A4. Sign-then-encrypt grows up

Replace the raw `SignerKey` path in `EncryptFlow.kt` with routing through
`FileSigner`, which unlocks hardware keys behind the biometric prompt.
Match the iOS exclusion: NFC security keys stay out of this flow (mid-encrypt
NFC tapping is a bad time; the guard mirrors `SignEncryptError.requiresSecurityKey`).
Whether RSA identities appear in this picker is open question 3.

Acceptance: sign-then-encrypt with a Keystore hardware key produces a bundle
that iOS and Android both decrypt with a named, trusted verdict.

### A5. RSA signing

The gap is routing, not crypto: `SSHSigner.sign` already produces
`rsa-sha2-512` from an `OpenSSHPrivateKey`, and the verifier already checks it.

- `FileSigner.kt`: replace the `SSH_RSA -> throw` arm with parsing the stored
  private key and calling `SSHSigner.sign`.
- `FileVerifier.publicWireOf`: return `SSHSig.rsaPublicWire(e, n)` for
  `SSH_RSA` identities instead of null, so your own RSA signatures verify as
  trusted.
- Encrypted RSA private keys (bcrypt-pbkdf) follow whatever the import path
  already did at store time; no new passphrase UI.
- Fixtures: `ssh-keygen -Y sign` / `-Y verify` with an RSA key, both
  directions, added to `generate-fixtures.sh` and `CrossImplFixtureTests`.

Acceptance: an RSA signature made in AgePony verifies with stock `ssh-keygen`,
and vice versa, under the `agepony` namespace.

## 3. Feature B — duress/decoy password wipe

`PLANNED_FEATURES.md` item 1 is the spec; this section only sequences it. The
short version of why it is big: the app has no app-owned password at all today
(`BiometricGate` delegates everything to the OS), so the decoy has nothing to
sit next to until an app-owned unlock path exists.

### B1. App-owned password unlock

- A password unlock offered alongside the existing biometric gate, not
  replacing it. Verifier stored as a slow hash (scrypt is already in core and
  cross-platform; reuse it rather than adding Argon2), wrapping the same vault
  master key the Keystore path wraps.
- Build it so the deferred tri-state unlock work (`PLANNED_FEATURES.md` item 3)
  can attach later without rework: the password path must not assume biometrics
  exist, and must not route through `unlockPlain()`.

### B2. The wipe

- One "wipe everything" path in `Vault.kt`: all identities, recipients, notes,
  signers (new in this release, do not forget them), and the Keystore master
  key material. Callable from the duress branch and from nothing else for now.

### B3. Duress behavior

- Constant-time comparison against real and decoy verifiers.
- No tell: post-wipe UI state-identical to wrong-password. Which of the two
  "afterward" designs we ship is open question 4, and it must be decided with
  iOS in the room, since a duress feature that differs per platform is a worse
  duress feature.

### B4. Tests

- The four acceptance criteria from `PLANNED_FEATURES.md` verbatim, including
  the statistical timing test. The timing test runs on-device in the
  DeviceTests checklist, not just under Robolectric/JVM where timing proves
  nothing.

## 4. Verification strategy

- `./gradlew :agepony-core:test` stays the fast gate; every core addition
  (AllowedSigners, RSA routing, hashed sign) lands with tests in the same
  commit.
- Cross-impl fixtures: extend `generate-fixtures.sh` with `ssh-keygen -Y`
  sign/verify material for ed25519 and rsa, plus at least one `allowed_signers`
  file, so interop is pinned by CI rather than by hand-testing.
- Device checklist: a new `AgePony_4.0.0_DeviceTests.md` in the shape of the
  3.1.0 one. Must cover: detached sign with each key class (software, hardware
  with and without biometric requirement, NFC security key with PIN), verify of
  trusted / unknown / invalid, allowed_signers round-trip against a real
  desktop, sign-then-encrypt cross-platform against iOS, and the duress timing
  and no-tell checks.
- Release artifact: clean-clone build exactly per `AgePony_3.2.0_Release.md`
  sections 4 and 5. Nothing in this release adds a dependency, so check A2
  (no Play libs in foss) should be unchanged; the new `allowed_signers` fixture
  files live under test resources and never enter the APK.

## 5. Order of work

Core first, UI second, duress last; each numbered step is testable before the
next starts.

1. AllowedSigners port + tests + fixtures (A1)
2. RSA routing + fixtures (A5, small and independent, gets the "yes it
   ships in 4.0.0" risk out early)
3. StoredSigner vault model + FileVerifier matching (A2)
4. Sign tab scaffold + detached sign flow, software keys first, then hardware,
   then security keys (A3)
5. Verify flow + badge + add-signer paths (A3)
6. Sign-then-encrypt routing upgrade (A4)
7. App-owned password unlock (B1)
8. Wipe path + duress branch + timing/no-tell tests (B2, B3, B4)
9. README truth pass, `PLANNED_FEATURES.md` updates (close items 1 here and on
   iOS's copy when its half ships), versionCode 10, `changelogs/10.txt`,
   release notes, device tests doc

## 6. Release mechanics

- `versionCode 10`, `versionName 4.0.0`, tag `v4.0.0` with the `v`, same as
  3.2.0.
- F-Droid: the open MR builds `v3.0.2` by hash and is still not to be touched.
  With `AutoUpdateMode: Version` + `UpdateCheckMode: Tags`, `v4.0.0` gets
  picked up on its own after the recipe merges. `changelogs/10.txt` should
  briefly recap 3.2.0 the way `9.txt` recapped the untagged 3.1.0, in case
  4.0.0 is the first version some F-Droid users ever see.
- Play: same clean-clone artifact, `versionCode 10` must beat every track,
  re-test against the Play-signed internal build. The QR "sharing vs scanning"
  copy issue from the 3.2.0 doc is still outstanding; fix the listing copy
  during this release at the latest.

## 7. Open questions

1. **Tab placement.** A sixth bottom-nav item is over Material's recommended
   five. Options: six anyway (closest to iOS), fold Notes and Text together to
   stay at five, or put Verify under Files and only Sign+Signers in the new
   tab. Needs deciding before A3 starts.
2. **Verify namespace.** Both apps sign under the `agepony` namespace. Should
   the verify screen also accept `file` (the `ssh-keygen -Y` default), so
   signatures made by plain OpenSSH users verify in-app? iOS currently says no.
   Cheap to add, worth matching on both platforms at once.
3. **RSA in sign-then-encrypt.** SETTLED: yes, RSA appears in the encrypt-flow
   picker alongside ed25519 and hardware keys (`ENCRYPT_SIGNING_TYPES`).
4. **Duress "afterward" state.** SETTLED: the wipe silently re-bootstraps an
   empty vault whose real password IS the decoy just entered. The coercer sees
   a working, empty app; the decoy keeps unlocking it; any other secret fails
   normally. No tell, retry-stable, and it can demonstrate compliance. This is
   the behavior spec iOS implements against.
5. **Duress vs. the deferred tri-state unlock.** SETTLED: 4.0.0 renames the
   biometric toggle's copy so "off" honestly reads as "no lock at all"; the
   full tri-state work stays deferred per the original scoping call.
6. **iOS timing.** SETTLED: Android ships duress in 4.0.0, no flag. iOS
   implements the same spec next release.
7. **Unlock secret kind.** SETTLED: the user chooses password or PIN at
   enrollment. Cosmetic only (keyboard type, stored as `unlockSecretKind`);
   the crypto path is identical, which keeps constant-time comparison one
   code path.
